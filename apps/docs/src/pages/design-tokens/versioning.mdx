## Production-ready versions

### ^3.0.0

This release introduces the Landmark surface system: a structural model for backgrounds built on four design tokens: `background.surface.base`, `background.surface.tone.1`, `background.surface.tone.2`, and `background.surface.floating`.

The token changes are additive. No existing token values change, and legacy tokens remain available alongside the new ones. What changes is the appearance: v3 ships a white page with toned containers, where the legacy model encoded a grey page with white cards. This is a significant change to the look and feel of HPE's brand, which is signalled by a major version.

For Grommet applications, v3 is available in `grommet-theme-hpe` v9.x.

To learn the model, see [understanding surfaces](./understanding-surfaces). To apply it, see [designing with surfaces](./designing-with-surfaces).

### ^2.0.0

This release, referred to as "v2-Landmark," provides production-ready support for HPE's refreshed visual identity (October 2025 - present). It introduces the new Landmark color palette and the HPE Graphik font face to align with the updated brand expression.

For Grommet applications, v2-Landmark is available by [grommet-theme-hpe v8.x](https://github.com/grommet/grommet-theme-hpe/releases/tag/v8.0.0)

In the [HPE Design System Figma Component Library](https://www.figma.com/design/HDckqS2MWhINfC8EIQPMV1/HPE-Design-System-Components-V2?m=auto&t=NjHwxPFWYTvhZTP5-6), this is the default theme.

## Migration

### Migrating from v2 to v3

v3 introduces the Landmark surface system. Because the token changes are additive and the legacy tokens continue to resolve to their current values, nothing in your product changes on upgrade. Adoption is opt-in and can happen incrementally.

When you migrate, map legacy tokens onto new ones **by role, not by value**. The table below shows the mapping. Colors will change, so treat that as intended. Migrating by value preserves today's appearance but assigns the wrong roles, and your product won't pick up future theme changes correctly.

| Legacy token | Replacement | Value relationship | Disposition |
| --- | --- | --- | --- |
| `background.back` | `background.surface.base` | Changes: grey-50 to white-100 | Deprecated in v3, frozen at its current value |
| `background.front` | `background.surface.tone.1` | Changes: white-100 to grey-50 | Deprecated in v3, frozen at its current value |
| `background.floating` | `background.surface.floating` | Identical | Deprecated in v3, aliased to its replacement |
| `background.default` | Audit per usage: `background.surface.base` or `background.surface.tone.1` | Depends on the usage | Not deprecated in this release |
| `background.contrast` | No replacement | Unchanged | Retained. Not a surface |

`background.back` and `background.front` are frozen at their current literal values rather than aliased to their replacements, so that upgrading does not silently flip every unmigrated page from grey to white. `background.floating` is aliased to `background.surface.floating`, because the values are identical at launch and remain so by construction.

`background.default` is not deprecated in this release and has no removal date, because it was used for two different roles and each use needs a per-use judgement. `background.contrast` is retained unchanged; it is not a surface.

Migration is not a colour swap. A design built on the previous convention will contain containers that existed only to lift content off a grey page, and those should be reevaluated.

#### Deprecation schedule

| Token | Values frozen | Deprecation | Removed |
| --- | --- | --- | --- |
| `background.back` | v3 | v3.x | Possibly v4 |
| `background.front` | v3 | v3.x | Possibly v4 |
| `background.floating` | v3 | v3.x | Possibly v4 |

### Migrating from v1 to v2

v2-Landmark introduces significant updates to align with HPE's refreshed visual identity. This is a major version change reflecting a new brand expression and includes breaking changes.

A full list of changes and detailed instructions can be found in the [Migrating from hpe-design-tokens v1 to v2-Landmark guide](https://github.com/grommet/hpe-design-system/wiki/Migrating-from-hpe%E2%80%90design%E2%80%90tokens-v1-to-v2%E2%80%90Landmark) and the [grommet-theme-hpe v7 to v8 Migration Guide](https://github.com/grommet/grommet-theme-hpe/wiki/Migrating-from-HPE-Theme-7.x-to-8.x).

### Migrating from v0.9.0 to v1.0.0

v1 reflects styling of the updated HPE theme.

For `hpe-design-tokens`, there are no breaking API changes from v0.9.0 to v1.0.0, so teams  
may upgrade directly to v1.0.0 without code modifications. However, it is recommended to 
review the [changelog](https://github.com/grommet/hpe-design-system/releases/tag/hpe-design-tokens%401.0.0) 
to understand the token value changes.

For `grommet-theme-hpe`, there are breaking changes. To make the upgrade process smoother,
the complete migration has been divided into to two steps. The first focusses on visual style 
treatments applied to components; the second introduces expanded t-shirt sizing options. Teams 
have the option to complete both steps at once or one at a time for greater flexibility.
1. Upgrade from v5.x to v6.x ([grommet-theme-hpe v5 to v6 Migration Guide](https://github.com/grommet/grommet-theme-hpe/wiki/Migrating-from-HPE-Theme-5.x-to-6.x))
2. Upgrade from v6.x to v7.x ([grommet-theme-hpe v6 to v7 Migration Guide](https://github.com/grommet/grommet-theme-hpe/wiki/Migrating-from-HPE-Theme-6.x-to-7.x))


## Semantic versioning

HPE Design tokens follows the standards defined by semantic versioning with slight adaptations at the major version level to align with hpe-design-tokens as a style delivery mechanism.

Given a version number MAJOR.MINOR.PATCH, increments will occur when:

**1. MAJOR version** when there is a significant change to HPE’s brand expression and/or there are incompatible changes to the API.

Significant changes to the look and feel of HPE’s brand &mdash; even if no breaking changes to the namespace are made &mdash; will be signaled via a major change (i.e. the look and feel of the new major version is not compatible with the look and feel of the previous).

This signals that if service A is on v1.y.z and service B is on v2.y.z, there will be a mismatch in overall experience.

**2. MINOR version** when there is functionality added in a backward compatible manner. Examples include:

- Introducing a new token.
- Updating a token value in an expected, minor way. For example, slightly darkening or lightening a text color based on user testing/feedback.

**3. PATCH version** when backward compatible bug fixes are made. Examples include:

- Fixing a typo in a token value.
- Fixing a color value to meet accessibility requirements.
