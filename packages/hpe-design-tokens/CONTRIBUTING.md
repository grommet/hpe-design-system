# Contributing To hpe-design-tokens

This guide is package-specific. For repository-wide contribution policies, also read `../../CONTRIBUTING.md`.

## Scope

Use this package when you are:

- Updating token source JSON in `tokens/`
- Changing token build/transforms under `src/`
- Running Figma sync tooling for test or production environments
- Updating sync contracts and schemas under `contracts/`

## Prerequisites

- Node.js and pnpm installed
- Repository dependencies installed from workspace root:

```bash
pnpm install
```

- Figma credentials/config present when running sync scripts:
  - Copy `.env.example` to `.env`
  - Populate environment-scoped values

## Local Development Workflow

1. Edit token source files in `tokens/`.
2. Run package tests:

```bash
pnpm --filter hpe-design-tokens test
pnpm --filter hpe-design-tokens test:contracts
```

3. If your change affects Figma sync behavior, validate in test first:

```bash
pnpm --filter hpe-design-tokens sync-tokens-to-figma -- --env=test --dry-run
pnpm --filter hpe-design-tokens sync-tokens-to-figma -- --env=test
pnpm --filter hpe-design-tokens sync-figma-to-tokens -- --env=test --output tokens_qa
```

4. Compare expected token diffs and ensure no unintended churn.

### Token Version Parity

When adding token paths, keep the corresponding default, v0, v1, and v2 JSON
structures aligned. For semantic colors that are not supported in a prior
version, set `$value` to `{color.transparent}`. Do not use `undefined` (which
is not valid JSON) or `null` for color values.

Keep the description, scopes, code syntax and
`com.figma.hiddenFromPublishing` identical in every mode file of a collection,
including the prior-version files. Figma stores them once per variable, not
per mode, so files that disagree are rewritten on every sync and the last file
read wins. A token that is published in the default modes is therefore
published in the prior-version modes too, where it resolves to transparent.

Primitive colors cannot reference the higher-tier `color.transparent` token;
use literal color values in primitive files.

## Tests And Where To Add Them

- `src/tests/token_version_parity.test.ts`
  - Checks token leaf paths and `$type` across default, v0, v1, and v2
    collections and modes, using the same shared-file fallback as token theme
    discovery. Values may differ between versions.
  - Checks that the description, scopes, code syntax and publishing flag of
    each token are identical in every mode file of its collection.
  - Run with `pnpm --filter hpe-design-tokens exec vitest run src/tests/token_version_parity.test.ts`.
- `src/tests/figma_sync_config.test.ts`
  - Add tests for config/env resolution and production guardrails.
- `src/tests/sync_events.test.ts`
  - Add tests for machine-readable event payloads and error normalization.
- `src/tests/sync_contract_schemas.test.ts`
  - Add tests when changing run-summary or stage-status payload shape.
- `src/tests/token_import*.test.ts`
  - Add tests for alias resolution and token import behavior.
- `src/tests/build.test.ts`, `src/tests/color.test.ts`
  - Add tests for build and token utility behavior.

## Sync Safety Rules

- Prefer `--env=test` for development and validation.
- Use `--dry-run` before mutating test files.
- Local production mutations require `--confirm-production`.
- CI production mutations require `ALLOW_PRODUCTION_WRITES=true`.
- Use `--bootstrap` only for first-time setup of fresh Figma files, then switch back to normal mode after discovering collection keys.

## Documentation Update Expectations

When behavior changes, update docs in the same PR:

- `README.md` for package entrypoints
- `docs/OPERATIONS.md` for runbooks and command usage
- `contracts/figma-sync-cli-contract.md` for command/flag/output contracts
- `contracts/figma-sync-failure-codes.md` for error code semantics

## Release Changesets

Add a Changeset for every user-visible package change. Use `patch` for non-breaking token value
corrections and accessibility fixes, `minor` for additive tokens or capabilities, and `major`
for removed or renamed tokens, incompatible aliases, or other breaking output changes. Include
the affected token families, consumer impact, and migration guidance. The release workflow turns
approved Changesets into a version and changelog PR for maintainer review. Pull requests that
change token values, contracts, or published package metadata must include a Changeset naming
`hpe-design-tokens`. For implementation changes, package development-dependency changes, or root
dependency-graph changes to `package.json`, `pnpm-lock.yaml`, or `pnpm-workspace.yaml`, the check
builds the pull request merge base and head revisions with their respective dependency graphs and
requires a Changeset only when the published `dist` artifacts differ. The version and changelog
update generated by the release workflow is exempt only for the GitHub Actions-created release PR
because it consumes the Changeset that already describes the release.

## Pull Request Checklist

- Tests pass locally for impacted areas
- Any sync-related change validated with test environment command examples
- Contract/schema updates included when payload behavior changes
- Docs updated for new flags, scripts, or safety semantics
